# 开源技术栈与许可证说明

> 基线：2026-11-03 初赛交付版本。文中版本号取自本机实际安装的 `node_modules`，不是 `package.json` 的版本区间。

本项目自身以 **MIT** 许可开源（仓库根 `LICENSE`，版权方 DeepSeek）。除模型能力外，平台全部运行在公开开源组件之上，没有私有框架或商业 SDK 锁定。

- 直接依赖 30 个，全部为 MIT / Apache-2.0 / BSD-3-Clause / MPL-2.0 系列。
- 全部安装实例 1654 个（按 `name@version` 去重），其中 MIT 占 78%，无 GPL / AGPL / SSPL 单许可依赖。
- 唯一使用**源码 vendor**（而非 npm 依赖）的开源部分是 Cordis 框架层，上游 MIT 许可证随源码保留。

## 1. 三种使用方式

| 方式 | 对象 | 说明 |
|---|---|---|
| 源码 vendor | Cordis 框架层（9 个包） | 复制进 `vendor/`，由本仓库构建和发布，可审计、可打补丁、可锁定 |
| npm 依赖 | 前端、服务端、测试链 | 常规 `dependencies` / `devDependencies`，走 pnpm 工作区 |
| 语言内置 | SQLite | 用 Node 内置 `node:sqlite`，不引入第三方 sqlite 驱动 |

## 2. 框架层：Cordis（源码 vendor）

平台是多 Agent 调度工作站，底座是 Cordis 这个全插件式 agent harness。选择 vendor 而不是 npm 依赖，原因是需要完全掌控框架层：插件加载顺序、服务生命周期、配置加载器都属于会改动核心逻辑的位置，锁在 npm 包外无法调试，也无法在比赛周期内跟上游节奏。

| 目录 | 上游包 | 上游版本 | 许可证 | 上游仓库 |
|---|---|---|---|---|
| `vendor/cordis/` | `cordiverse/cordis`（packages/core） | 4.0.0-rc.7 | MIT | github.com/cordiverse/cordis |
| `vendor/loader/` | `@cordisjs/plugin-loader` | 1.0.0-rc.5 | MIT | github.com/cordiverse/cordis |
| `vendor/include/` | `@cordisjs/plugin-include` | 1.0.4 | MIT | github.com/deepseek-harness/cordis |
| `vendor/group/` | `@cordisjs/plugin-group` | 1.0.0 | MIT | github.com/deepseek-harness/cordis |
| `vendor/timer/` | `@cordisjs/plugin-timer` | 1.1.4 | MIT | github.com/cordiverse/cordis |
| `vendor/hmr/` | `@cordisjs/plugin-hmr` | 1.0.15 | MIT | github.com/deepseek-harness/cordis |
| `vendor/logger-console/` | `@cordisjs/plugin-logger-console` | 1.0.0 | MIT | github.com/deepseek-harness/cordis |

| `vendor/schemastery/` | `schemastery` | 3.18.0 | MIT | github.com/deepseek-harness/schemastery |

合规做法：

- 9 个包的上游 `LICENSE` 原样保留在各自目录下，未改写、未删除。
- 本地改动逐条记录在 `vendor/README.md` 的 “Local modifications” 一节，可逐条对照上游 diff。
- vendor 包的第三方依赖仍走 npm（`js-yaml`、`chokidar`、`picomatch` 等），不二次 vendor。

## 8. 非开源依赖：模型 API

平台的推理能力来自 **DeepSeek 模型 API**。它是托管服务，不是开源组件，也不随仓库分发：

- 仓库内不含任何 API key，`.env` 已被 gitignore，CI 里只有 `secrets.*` 引用名。
- 真实 API 端到端测试在缺少 `DEEPSEEK_API_KEY` 时自动跳过；带 key 的 E2E workflow 在公开仓库上会因 preflight 硬失败而红叉，这是密钥不入库的代价，属已知取舍。
- 评审侧无需模型 key 即可复现：单元测试、类型检查、构建、以及基于录制回放的 snapshot 测试都不依赖外部推理。

## 10. 自研边界

为了避免“用了开源框架就等于套壳”的误解，这里明确划界：

| 层 | 归属 |
|---|---|
| Cordis 框架层（插件加载、服务生命周期） | 上游开源，本仓库 vendor 并做本地改造（改动有记录） |
| 多 Agent 编排、调度决策、任务 DAG | 自研（`packages/experimental/future-cup-orchestration/`） |
| SelfLoop 自愈、验证流水线、证据归档 | 自研 |
| 管理平台 UI（工作台、大屏、移动端） | 自研（`future-cup-platform/ui/`） |
| 其余 300+ 个 harness 能力包 | 自研（`packages/`，371 个 workspace 包） |
| 模型推理 | 外部 API，非开源组件 |

## 11. 复现

```sh
pnpm install                 # pnpm 11.28.5，Node >= 24.9
pnpm run typecheck           # TypeScript 6.0.3
pnpm run test                # Vitest
pnpm run build               # tsdown 产物
pnpm run test:snapshot       # 录制回放，无需模型 key
```

管理平台单独启动（Windows 双击 `启动平台.bat` 等价于下式）：

```sh
pnpm start:platform          # 需要 DEEPSEEK_API_KEY；端口 3090
```

## 1. 执行摘要

Future Cup 是一个面向 Web 前端工程交付的多 Agent 编排与自验证平台。系统接收自然语言需求，由 Planner 生成页面计划和任务 DAG，通过可解释调度器分配 Agent，在独立 DeepSeek Harness Session 中完成设计、测试规划、页面开发、集成和失败修复，最后由独立 Verifier 执行 TypeScript、Vite 和 Playwright 验证。

项目不是从零实现 Agent Runtime，而是在 DeepSeek Harness 和 Cordis 基础上自主研发平台层。Harness 负责单 Agent Runtime、Session、模型与工具；Future Cup 负责多 Agent 团队、持久 DAG、调度、工作流控制、Self-loop、验证和交付。

当前系统已在最终 HEAD 上完成真实 DeepSeek 七人团队 E2E。系统能够冻结用户团队版本，启动 7 个独立 Agent Home，完成 6 个生成 Session，注入 TypeScript 故障，启动 1 个独立 Repair Session，并完成 `FAIL → PASS` 复验。

## 2. 产品定位与边界

### 2.1 目标场景

- 用户用自然语言描述一个前端工程需求。
- 系统自动分析页面、组件、依赖和验收要求。
- 多个专业 Agent 协同完成 React、TypeScript、Vite、Ant Design 工程。
- 系统通过真实构建和浏览器检查判断结果，不依赖 Agent 自述成功。
- 失败进入有界 Repair 子流程，最终交付带验证证据的工程。

### 2.2 初赛范围

- 单一受控技术栈：React、TypeScript、Vite、Ant Design。
- 受控 Agent 角色和受控工具权限。
- 持久 DAG、版本化团队、条件分支、有界循环、Repair 子工作流。
- 独立构建、浏览器验证、截图和交付预览。
- 管理 SPA、实时事件和只读 HQ 3D 大屏。
- 真实 DeepSeek E2E 和系统完成度证据。

### 2.3 暂不纳入初赛

- RAG、向量数据库和外部知识库。
- 实际 MCP Server/Client 工具接入。
- A2A、通用插件市场、任意工具安装。
- 公网多租户、计费、企业身份与权限系统。
- 任意拖拽工作流编辑器和任意 Agent 市场。

## 3. 总体架构

### 3.1 控制面

控制面由 `future-cup-orchestration` 和 `future-cup-platform` 组成。

- `future-cup-orchestration`：项目、任务、DAG、调度、Agent Registry、团队、项目记忆、工作流、验证和 Repair。
- `future-cup-platform`：Fastify REST、Socket.IO、Outbox、SQLite/PostgreSQL、真实团队启动器、静态 UI、截图和交付预览。
- Cordis：插件组合、配置层叠、资源生命周期和应用启动。

### 3.2 执行面

- 每个 Agent 使用独立 `DeepSeekHarness` runtime。
- 每个执行使用独立 Session 和 DSH Home。
- 默认模型为 `deepseek-official / deepseek-flash`。
- 默认 reasoning effort 为 `off`。
- 单 Agent 最大输出为 32,000 token。
- 单次请求超时上限为 600 秒。
- Agent 暴露 `read`、`read_image` 和 `working_directory` 工具。
- Bash、PowerShell、文件写入和文件编辑工具被禁用。

### 3.3 展示面

- React 18 单页管理应用。
- Ant Design 6 管理组件与主题。
- React Router HashRouter。
- React Flow 任务 DAG 和工作流控制图。
- Socket.IO 实时产品事件。
- HQ WebGL 只读大屏。
- 生成项目生产构建预览。

### 3.4 技术选型

- Harness 原生 Workflow 缺少持久 DAG、Journal、恢复和调度，因此不作为平台权威工作流。
- 平台使用自研持久 DAG 和版本化控制图。
- LangGraph.js 暂未引入，避免多个工作流生命周期真源。
- SQLite 用于本地运行和确定性测试。
- PostgreSQL + Prisma 用于配置后的持久化环境。
- Fastify + Zod 负责 REST API 和输入校验。
- Socket.IO + Outbox 负责已提交事件实时投递。
- Playwright 负责独立浏览器验证。

## 4. 核心运行链路

1. 用户创建项目并选择已发布团队版本。
2. 系统冻结团队版本、Agent 版本、工具权限、记忆策略和输出契约。
3. Planner 生成页面计划和任务 DAG。
4. DAG 校验环、依赖和任务范围。
5. Scheduler 计算候选 Agent 得分并持久化选择依据。
6. 各 Agent 使用独立 Harness Session 执行任务。
7. 结构化输出经 Zod 校验后，由平台按写入范围落盘。
8. 两个 Frontend 任务并行完成后，由 Integration 汇总。
9. Verifier 执行结构、依赖、TypeScript、Vite 和 Playwright 检查。
10. 失败报告生成稳定失败签名并进入 Repair 子工作流。
11. Repair 后重新执行完整验证。
12. 成功进入交付和预览；重复失败或轮次耗尽进入人工升级。

## 5. Agent 角色与团队

| 角色 | 职责 | 主要输出 |
|---|---|---|
| Planner | 分析需求并生成页面与任务 DAG | 页面、任务、依赖、能力要求 |
| UI Designer | 生成共享视觉系统和设计 token | 设计说明、颜色、字体、间距 |
| Tester | 定义确定性浏览器验收规格 | 路由、必需文本、导航交互 |
| Frontend | 实现单个页面 | 最多 3 个 `src/pages/` 文件 |
| Integration | 集成路由、共享导航和页面 | 最多 8 个 `src/` 文件 |
| Verifier | 独立验证系统结果 | 验证检查项和 finding |
| Repair | 根据结构化失败修复源码 | 最多 8 个 `src/` 文件 |

默认团队包含 7 个运行时实例：Planner、UI Designer、Tester、Frontend A、Frontend B、Integration 和 Repair。系统 Verifier 由平台拥有，不计入运行时成员数。

用户团队库支持 1 至 7 个实例、不可变版本、发布、克隆、归档和项目引用查询。项目启动后使用冻结快照，后续团队编辑不影响历史项目。

已验证项目可以派生新的升级后继项目。平台复制来源项目的冻结团队与项目记忆，记录来源运行和升级需求，并为新项目启动独立运行。升级模式从来源项目的不可变交付快照恢复源码；重新生成模式从空工作区开始。旧项目的验证、修复和交付证据保持不变。

## 6. DAG、工作流与调度

### 6.1 DAG

- 状态：`PENDING`、`READY`、`RUNNING`、`COMPLETED`、`FAILED`、`BLOCKED`、`CANCELLED`。
- 创建和恢复时拒绝环、重复任务和缺失依赖。
- 任务完成推进下游 READY。
- 任务失败或取消阻断下游。
- 每次状态变化写入 Journal，并带单调 revision。
- 恢复时重放 Journal，并与当前任务快照逐项校验。

### 6.2 控制图

- 节点类型：`TASK`、`SEQUENCE`、`PARALLEL`、`CONDITION`、`LOOP`、`SUBWORKFLOW`、`TERMINAL`。
- `PASS` 进入交付。
- `FAIL` 或 `INCOMPLETE` 进入 Repair 循环。
- Repair 完成返回验证。
- 默认最多 3 轮自动修复。
- 节点进入/完成、边选择、循环和子工作流事件均持久化。
- 控制快照使用 revision 防止旧写入覆盖新状态。

### 6.3 调度

```text
capabilityMatch * 0.50
+ historicalSuccessRate * 0.20
+ availability * 0.15
+ priorityRatio * 0.15
- loadRatio * 0.35
```

标准调度结果记录候选 Agent、能力、历史成功率、可用性、负载、得分、拒绝原因和最终选择。重试时可排除上一 Agent；同角色存在替代实例时重新分配。所有实例满载时，任务延后到下一轮。

## 7. 验证与 Self-loop

### 7.1 验证流水线

1. 工程结构和必需文件。
2. favicon 和 HashRouter 契约。
3. 依赖安装。
4. TypeScript 检查。
5. Vite 生产构建。
6. Loopback 预览服务器启动。
7. Playwright 桌面 1440×900 和移动 390×844。
8. 可见内容、必需文本和跨页导航。
9. 页面异常、控制台错误、Ant Design 弃用告警、失败请求和 HTTP 4xx/5xx。
10. 验证截图和结构化报告。

浏览器不可用时只能产生 `INCOMPLETE`，不能产生 `PASS`。

### 7.2 自适应 Repair

- 失败类别包括结构、依赖、TypeScript、构建、服务器、浏览器、控制台和网络。
- 验证消息规范化为稳定 SHA-256 失败签名。
- 修复策略按类别、目标路径、特异性和历史使用情况评分。
- 重复签名优先使用未执行过的新策略。
- 策略不能改变验证阈值。
- 每次修复必须执行完整复验。
- 超时、Repair 失败、验证不完整、策略耗尽或重复失败均进入 `ESCALATED`。

## 8. 持久化与实时事件

- SQLite 物理 schema 为 v8，支持 v1 至 v8 原地迁移。
- PostgreSQL 使用 Prisma 和正式 migration。
- 项目事件包含 `projectId`、项目内 `seq`、时间、类型和 JSON payload。
- 产品事件和 Outbox 在同一事务提交。
- Socket.IO 使用 `projectId + afterSeq` 恢复快照与增量。
- 客户端按 `projectId + seq` 去重。
- 事件序号缺口触发权威快照重新同步。
- 工作流 lease 保存 owner、heartbeat、expiry 和 fencing token。
- 领域写校验 fencing token，旧 owner 不能覆盖新状态。

## 12. 安全、许可与限制

- 当前 Agent 暴露的工具只有 `read`、`read_image` 和 `working_directory`；Bash、PowerShell、写入和编辑工具被禁用。
- 平台仍在宿主机执行依赖安装、TypeScript、Vite 构建和 Playwright。
- 当前服务仅绑定 loopback，无公网认证和 TLS。
- 本轮未重新执行 PostgreSQL E2E，PostgreSQL 证据来自既有 M4.1 验收。
- HQ 资产为非商业许可，不能当作项目完全自研资产。
- 最终 E2E 存在模型服务重试和耗时波动，不应作为稳定性能基准。

### 12.1 容器隔离核验

核验结论：容器隔离未接入主运行链路，该结论成立。

- `run-launcher.ts` 在宿主机 `workspaceRoot` 下创建运行目录，并把该目录作为 `TeamOrchestrator` 的工作区。
- `build-verifier.ts` 默认使用 `localVerificationCommandRunner`，通过 `execFile` 在宿主机工作目录执行 `npm install`、`npm run build:types` 和 `npm run build:bundle`。
- `future-cup-orchestration/src` 和 `future-cup-platform/src` 中没有 Docker、Podman、SWE-ReX 或容器创建逻辑。
- 最终 E2E 的数据库记录使用本机路径：`D:\Users\tr666\Documents\ChatGPT\ruiruiai\.artifacts\future-cup-m55-live\real-team-GJm5ZY\workspaces\future-cup-run-13191135-61f9-407c-b67f-a764ca6e4fcd\workspace`。
- 该工作区中实际生成了 `node_modules` 和 `dist`，证明依赖安装和生产构建在宿主目录完成。
- 当前主机未安装 `docker`、`podman` 或 `swe-rex` CLI，最终 E2E 不依赖这些命令。
- M1 的 Docker 29.7.2 和 SWE-ReX 1.4.0 结果来自独立技术验证，只能证明方案可行，不能证明主运行链路已使用容器。

因此初赛材料应表述为：

> 已完成容器隔离方案的技术验证；当前平台 Agent 权限受限，但生成工程依赖安装、构建和浏览器验证仍在宿主工作区执行，容器隔离将在后续阶段接入主运行链路。

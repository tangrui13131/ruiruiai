# Agent Note: Future Cup multi-agent orchestration platform

## Problem

未来杯竞赛要求交付一个面向大语言模型 agent 工具编排与调度（orchestration and scheduling）的完整工程化平台。评审覆盖知识库定义与集成、Agent 团队定义、工作流编排、动态调度、self-loop 执行，以及结果验证与反馈优化。只会调用工具的单个 agent、API 壳子、纯 PPT 概念，或者未经实质改造的框架示例，都不能满足提交规则。

DeepSeek Harness 已经提供并发 Session、上下文隔离的 subagent Session、包含 Lead、teammate、共享任务 DAG 与直接 inbox 投递的实验性 Agent Teams，以及支持 rewind 与 fork 的 Session 事件日志。它没有提供质量验证体系、依据上下文压力和 agent 能力作出反应的调度策略、有界修复循环，或者用于组合并观察这些机制的产品界面。

项目需要在开始实现前持久记录竞赛约束、选定技术方向、候选业务场景与 MVP 顺序。没有这条记录，后续工作容易退化成框架演示，在产品外壳尚未证明自愈闭环时过度建设，或者优化一个缺少客观成功判据的场景。

## Proposal

把竞赛平台构建为 DeepSeek Harness 上的一组 Cordis 插件与产品界面。保留原生 Session 日志、subagent 与 Agent Teams 机制作为执行基础。围绕这些机制增加调度器、验证流水线、有界 self-loop、工作流编辑器、实时沙盒与执行 trace，而不是另建一套替换它们的编排器。

平台必须使用具有不同角色和独立 Session 的多个 agent。Lead 负责拆解、调度决策与最终汇总。teammate 实现或检查边界明确的任务。对于确定性检查无法完全判断的内容，由独立 Verifier Agent 审查证据。通信与状态转换必须能通过持久 Team 任务与 Session 记录观察。

为竞赛发布的仓库必须说明哪些部分来自 DeepSeek Harness 上游项目，并列出全部改动与新增创新。仓库必须提供部署说明、测试用例与可复现的演示路径。凭据只能从环境变量加载，绝不能提交。

### Competition constraints

- 交付物必须是 multi-agent orchestration platform，不能是单个 agent 工具调用演示或薄模型 API 壳子。
- 必须提供可运行原型；概念幻灯片和伪代码不合格。
- 至少一种 self-loop 必须执行真实的验证与修正周期。
- 产品中必须体现知识库集成、Agent 团队定义、工作流编排、动态调度、self-loop 执行、验证与反馈优化。
- 提交物包含至少 5,000 字中文技术方案书、10-15 页幻灯片、3-5 分钟端到端演示视频，以及含部署文档和测试的可复现仓库。

### Platform capabilities

- **知识库：** 把项目知识、工具约定、编码规则、验证证据与检索来源定义为平台资源。初始实现使用工作区文档与测试 fixture（测试前置数据）；后续适配器可以接入外部 RAG（检索增强生成）索引。
- **Agent 团队：** 为 Lead、worker、reviewer 与专用 Verifier 定义角色、模型、skill（技能）、工具权限、上下文预算与交接规则。
- **工作流编排：** 把工作表示为 DAG，节点声明输入、输出、依赖、执行者要求与验证标准。可视化编辑器负责创作 DAG，运行时以持久 Team 任务记录作为权威状态。
- **动态调度：** 根据 agent 技能匹配度、当前上下文占用量、并发容量、依赖就绪状态与历史失败选择可运行节点。调度器可以增加聚焦修复节点、重新分配任务，或者裁掉输出已不再需要的节点。
- **Self-loop：** 在 teammate Session 内执行有界局部修复，再把未解决问题升级给 Lead 进行范围更大的重规划或 rewind。
- **验证与反馈：** 组合静态检查、沙盒执行证据、确定性测试与 Verifier Agent。保存判定结果与修复证据，使后续调度使用实际观察到的结果。

### Adaptive scheduling

调度器把可运行的 DAG 节点放入有界并发池。它依据声明的 agent 技能匹配度、token 上下文占用量、依赖关键程度、历史成功率，以及再次修复的成本对候选任务排序。超过上下文水位线的 agent 不再接收新的实现任务，直到它完成压缩、fork 或把任务交给更合适的 teammate。

运行时变更必须显式且写入日志。当验证否定某个分支时，调度器裁掉依赖被拒输出的下游节点，重新排队受影响工作，并记录 DAG 变化原因。重规划不是隐藏重试循环；每次节点增加、重新分配、抑制或回滚，都必须可以从 Session 事件与 Team 任务 revision 重建。

### Verification and self-loop

验证使用互补证据。静态分析在执行前捕获语法、类型、schema 与策略错误。沙盒运行生成的产物并捕获退出码、stdout、stderr、浏览器 console 错误、失败请求与预览状态。独立 Verifier Agent 根据收集的证据检查任务要求，可以拒绝那种“能运行但没有实现需求”的结果。

微循环在所属 teammate Session 内运行。验证失败会把结构化证据返回该 teammate，最多修复三次。修复成功后进入下一验证阶段；次数耗尽、超时，或者连续三次等价失败时停止局部循环。

宏循环属于 Lead。它接收失败证据，在需要时 rewind 或 fork 执行路径，改变任务拆解或 agent 分配，并通过 mailbox 发送新的有界任务。Loop Guard 限制尝试次数、实际耗时、token 与无进展时间。它产生可见的终止失败，而不是允许无限重试。

反馈优化使用持久验证历史。调度器可以降低对相同失败签名反复失败的 agent 或策略的优先级，并优先选择此前 fork 中发现的有效修复路径。MVP 只使用可观察调度信号，不引入不可解释的学习模型。

### Product interface

产品包含三个联动界面。React Flow 画布编辑 Agent 团队与工作流 DAG。沙盒面板展示生成的页面或应用，热重载已接受修订，并暴露捕获的运行时错误。执行 trace 按时间顺序展示任务归属、mailbox 交接、验证判定、修复尝试、rewind、fork 与最终汇总。

可视化编辑器不能成为第二个权威来源。它提交并渲染由 Host 拥有的持久工作流状态。trace 与预览根据执行和 Session 证据生成，因此刷新后的客户端可以重建此前状态。

### Candidate scenario and MVP

首选场景是微前端与运营 H5 编排平台。用户输入页面需求；多个 agent 生成组件代码与集成代码；沙盒渲染结果；故意注入的运行时错误造成白屏或 console 失败；Verifier 拒绝该修订；微循环执行修复，或者宏循环 rewind 并重新分配任务；修复后的页面热重载成功。可见结果与捕获到的失败到成功转换，使这个场景最适合竞赛演示。

三个备选场景保留客观验证信号：

- 企业级微服务漏洞定位平台使用失败单测的退出码与定向测试证据作为退回信号，再把代码送回修复。
- 上市公司财报穿透分析平台使用会计恒等式、跨报表勾稽规则与带引用 RAG 证据，拒绝无依据结论。
- 重大工程招投标资质审查平台执行废标条款检查，并要求 self-loop 补齐缺失证据，同时不得覆盖一票否决结论。

MVP 使用首选场景。其他场景只在核心闭环稳定后继续，不会在通过初赛前并行实现。

### Delivery order

战术目标是用一个小而可靠的演示通过初赛。实现顺序如下：

1. 组合现有 Agent Teams profile，证明一个 Lead、至少两个角色不同的 teammate 与一个 Verifier 能在独立 Session 中完成一次工作流。
2. 在 worker 到 verifier 的路径上增加确定性验证与沙盒证据捕获。
3. 实现三次修复微循环、Loop Guard、mailbox 升级，以及一条 rewind 或重新分配路径。
4. 增加最小执行 trace 与沙盒预览，让失败、修复与恢复过程可见。
5. 增加 React Flow 创作界面、知识与团队定义表单、部署文档、测试、技术方案书、幻灯片与演示视频。

前端广度与文档打磨排在工作闭环之后。它们不得先于以下证据：平台能够拒绝坏结果，在有界条件下修复，并展示恢复过程。

## Alternatives considered

**用一个带工具的模型包装成 Agent 平台。** 已否决，因为竞赛明确排除单 agent 调用路径或 API 壳子，提交物也无法展示团队协作、调度或有意义的 self-loop。

**提交默认 Agent Teams 示例并做外观改动。** 已否决，因为该示例提供协作原语，却没有质量验证、上下文感知调度策略、循环边界、产品工作流或声明明确的改动集合。它也违反开源底座必须披露实质修改的要求。

**从零构建独立编排器。** 已否决，因为 DeepSeek Harness 已拥有持久 Session、subagent、Team 任务、inbox 投递与 rewind/fork 行为。替换它们会增加实现风险，并削弱演示的可追踪性。

**在初赛实现全部四个业务场景。** 已否决，因为各场景需要不同的验证工具、领域知识与用户界面。一个完整且有稳定测试路径的失败到恢复演示，比一个宽而浅的平台更有说服力。

**在修复闭环可用前先完成完整可视化平台。** 已否决，因为缺少可运行 verifier 与有界恢复时，精致画布仍无法通过核心技术评审。先实现闭环及其证据，再由界面展示已验证的行为。

**无限重试，直到模型偶然成功。** 已否决，因为等价错误会消耗时间与 token，却不保证进展。平台必须提供可见的无进展边界与升级后的终止状态。

## Acceptance criteria

- 可复现演示从声明的页面需求开始，创建 Lead 与至少两个不同 teammate，执行 DAG 并汇总结果，同时不造成父子上下文交叉污染。
- 确定性注入缺陷被静态或运行时证据拒绝，结构化报告进入所属 teammate，并触发最多三次局部修复。
- 修复继续失败时，Loop Guard 停止局部重试、记录失败签名、通过 Team mailbox 升级，并执行或调度恰好一条有界 rewind、fork 或重新分配路径。
- 修复后的产物在沙盒中成功预览，执行 trace 可以重建任务归属、任务 revision、mailbox 交接、验证证据、修复尝试、rewind 或 fork，以及最终成功。
- 动态调度决策展示选中的 agent、上下文水位证据、依赖就绪状态、并发状态，以及节点增加、裁减或重新分配的原因。
- 测试覆盖成功验证、可修复失败、修复耗尽、重复错误熔断、依赖节点裁减，以及客户端从持久状态重建。
- 仓库明确标注上游代码与修改代码，不包含已提交凭据，并记录安装、环境配置、测试与演示流程。
- 最终提交物包含规定的技术方案书、10-15 页幻灯片、3-5 分钟演示视频与完整可复现仓库。

## Risks

- Agent Teams 及相关 Session API 仍是实验性的，可能变化。竞赛分支需要固定上游 revision，并提供明确适配测试。
- 浏览器 console 捕获与预览恢复可能受时序影响。演示需要确定性故障注入，以及不依赖瞬时动画时序的证据收集。
- 技能匹配与 token 水位分数可能看起来像算法，却没有改善结果。MVP 必须展示可测量调度效果，例如在固定基准上减少上下文溢出失败或缩短完成时间。
- 复杂任务可能不适合三次修复限制。该边界是竞赛安全默认值，必须按部署可配置，不能在插件代码中静默改变。
- Verifier Agent 可能批准看似合理但实际错误的结果。有确定性检查时，以其为权威，Agent 判定必须引用审查过的证据。
- 四个候选领域会分散实现精力。初始端到端路径只包含首选的微前端场景。
- 初赛周期较短。交付物、测试与录制演示属于验收工作，不是代码完成后的清理工作。
